# 法务云与数据云的反馈飞轮

**来源**：2026-10-09 对话整理（对话原文见 git 历史）  
**状态**：未验证假设，启动条件与验证方式见文末。

## 机制

法务云的核心资产是合规规格书——把法规与审核口径翻译成数据云可执行的结构化规则，其质量取决于对审核方意图的理解深度。数据云的核心资产是生成流程模板——针对任务类型设计的提示链、生成轮次与质量校验。数据运营产生的驳回反馈同时喂养两层。

反馈对法务云是规格书的实测校验：某类风险被驳回「覆盖不足」，说明该类风险的描述颗粒度不够，需要细化到具体变体；某类材料被驳回「不符合属地要求」，说明规格缺少地区差异化参数；某种表述被认可，说明对应措辞模板有效，可固化。每一条驳回都在回答同一个问题：规则写到什么程度，生成才能通过。

反馈对数据云是流程的鲁棒性信号：产出模板化则调整提示、增加多样性约束；对抗性不足则加入多轮诱导生成；数量不足则修正生成参数；格式不对则固化格式校验规则。每一条驳回都定位流程中不够鲁棒的环节。

两层互相促进：规格书越精准，生成越有的放矢；通过率越高，规格书的有效颗粒度得到确认并固化进标准模板，同类任务下次直接调用。生成结果持续被驳回时，这个信号会触发规格书重审——是规则理解错了，还是规则本身需要更新。

## 启动条件

一是反馈必须结构化。客户的驳回意见是自然语言，需要产品化引导其提供可归因的信息：驳回类型、具体类别、审核方原话。没有结构化反馈，两层都不知道该改哪里。

二是归因必须清晰。同一条驳回可能是规则问题（规格没写清楚），也可能是执行问题（未按规格生成）。需要在产品里设计归因标签，让反馈自动路由到对应的层——否则两层都认为不是自己的问题，飞轮卡死。

## 飞轮的壁垒

运转一段时间后积累两样东西。法务云侧：一份持续更新的合规规格库——不同备案类型、地区、行业的规格书模板，及每条规格背后的有效与无效验证记录。数据云侧：一套经实战校验的生成流程库——各任务类型下有效的提示策略、必要的校验规则、通过率最高的参数组合。两者合起来是一个用真实反馈训练出来的合规数据生成系统；后来者可以抄产品界面，抄不走从一条条驳回里长出来的规格库与流程库。

## 验证切口

最小验证阶段手动跑飞轮：找三至五个小团队免费生成材料，跟踪提交结果，逐条人工归因驳回意见、手动更新规格与流程。跑完一轮即可看清哪些反馈重复出现、哪些归因高频、哪些修正真正提升通过率。先手动验证飞轮方向，再产品化放大飞轮速度。
